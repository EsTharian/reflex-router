# Phase 1 acceptance

Run 2026-09-19 against the M5 commits on top of `7da9d49` and the archived logs under `~/.reflex/archive/`. This merges the eight-point checklist of `docs/m5-handoff.md` (§5, items H1–H8) with the ten acceptance criteria given for M5 (U1–U10) into one list of 14 items. Each item names the source items it covers.

**How it was run.** Nothing here comes from a new interactive Claude Code session: the archived logs are from the earlier acceptance sessions (shadow dogfood, route A/B/C, M4), which ran on the M2–M4 builds. M5 changed no decision, wire, guard, policy, backend, outcome or privacy logic. The one change under `src/worker` and `src/log` is the additive `timing` block of the decision record (section 7): it measures and records, and nothing reads it back. So those sessions still describe how the code decides. Archive-derived checks are reproducible with `node scripts/acceptance/check-archives.mjs` (reads the logs only; exit 1 on any FAIL). Test-derived checks are `npm test`.

**Status words.** MET = checked and holds. MET (tests) = holds according to automated tests; no real session exercised it. PARTIAL = part holds, part does not or was not shown. NOT MET / NOT RUN say so.

## Evidence

**1. Off.** `test/integration/launch.test.ts` ("off is literally plain claude"): argv and base URL untouched, no `--settings`, the backend key not handed to `claude`, nothing on stderr. Spot check with the real binary: `REFLEX_MODE=off node bin/reflex.js --version` prints `2.1.277 (Claude Code)`, exit 0. No interactive session was run in `off` mode.

**2. Shadow.** `shadow-1.jsonl` (61 records, one session): 12 `new` turns (11 main, 1 subagent), every one has a backend decision; the backend is asked for `new` turns only; 0 degraded records, 0 shape violations, mode `shadow` throughout; 0 `unclassified`; all 61 requests forwarded on the requested model, none rewritten (checks 2a–2e). Turn accounting against Claude Code's own transcript (counts and flags only): 14 transcript "prompts" are 11 typed prompts, each with exactly one `new` decision in its window, plus `/compact`, one background-task notification (classified `side/notification`) and the compaction summary Claude Code wrote (`isCompactSummary`), none of which is a typed turn. Byte-identical forwarding and no added critical-path latency are asserted by `shadow.test.ts` ("replays every fixture", "a hanging backend adds no latency"); a log cannot show them. Limit: shadow-1 was recorded on the M2 build, before the keep-alive client and the `mass` rule; a shadow session on the current build was not re-run.

**3. Subagent routing and pinning.** Three routed subagents across the archives: `route-1` Opus → Sonnet twice (7 and 6 continuations), `m4-acceptance` Opus → Haiku (5 continuations); every continuation went to the same tier with `pin: hit` (check 3). Also `route.test.ts` ("its continuation reuses the pin … with zero Jev calls").

**4. Main chat.** 8 rewritten main-chat `new` turns in the route archives, each either passed the guard or did not leave the cache holder's tier: `guard:fresh` 2, `stay_pinned` 3, `return_up` 2, `override` 1 (the guard is evaluated only when a turn would move to a cheaper tier than the one holding the cache; staying and moving up are not guarded, by design in `src/worker/router.ts`). 17 guard refusals (`over_limit`, `ctx_unknown`), none rewritten to a cheaper tier. In the post-fix archives (`route-2`, `route-3`, `m4-acceptance`) every refused turn was sent on the tier the conversation was already on. Session B repeat (`route-3`): Haiku (override) → Sonnet (`return_up` on Jev's own pick) → Opus only by explicit override → refused by the guard and stayed. The pre-fix archive `route-1` still contains the bug this criterion is about (one refused turn went back to Opus); it is the reason for the `stay_pinned` fix and is reported as a NOTE by the script, not counted. Note the Sonnet step in `route-3` is a move up by the backend's pick, not a return to Opus.

**5. Overrides.** 4 override records: `reflex:haiku` and `reflex:opus` in `route-2` (the Haiku one rejected upstream for the long-context beta and re-sent on Opus, see 6; the Opus one `same_tier`), and the same pair in `route-3` after the beta fix (Haiku applied, Opus applied). `!` is not accepted: `src/overrides.ts` parses only `reflex:<tier>`, because Claude Code consumes `!` as bash mode. An override skips the backend, the confidence rule and the main-chat cost guard (README now says so).

**6. Rejected rewrite.** 2 fallback records: both show the requested model as sent, `rewritten: false`, and the re-sent request's status 200. `route-2` (B1) carries the upstream's message (`invalid_request_error: The long context beta is not yet available for this subscription.`); the `route-1` (A1) record has status 400 but no message because it predates the `fallback_error` field, so "error message logged (A1, B1)" holds for B1 only. Byte-identical re-send is asserted by `route.test.ts` ("a rejected rewrite is retried once with the original bytes; the tier is then disabled for the session"; "a rejected Haiku rewrite is retried with the original headers, beta included"). All 42 rewritten records in the archives list requested model, sent model and a non-empty `fields` list.

**7. Fail-open.**
- Jev unreachable: 3 archived records with `backend:timeout` (session C), all forwarded on the requested model, unchanged, upstream 200. They reached the upstream after 4,532, 1,388 and 903 ms; those records predate the timing block, so the log cannot separate the decision wait from the model's own first-byte time. From this build on every decision record carries `timing{decision_wait_ms, decision_deadline_ms, upstream_first_byte_ms}` and `reflex report` (section 6) checks timed-out decisions against deadline + 250 ms grace, so the next recorded session can verify it (`check-archives.mjs` 7c does the same over archives; it currently reports the three old records as unverifiable). Until then "within the deadline" rests on `route.test.ts` ("a hanging backend fails open within the deadline …", now also asserting `decision_wait_ms` between 450 ms and 500 ms + grace for a 500 ms deadline) and `shadow.test.ts` (breaker after 3 failures; shadow records `decision_wait_ms: 0`).
- Corrupt config: `launch.test.ts` ("an invalid configuration fails open: warn and run plain claude"). No archived session shows "C's first attempt"; it is not evidenced beyond that test.
- Worker `kill -9`: `door-worker.test.ts` ("kill -9 of the worker: the next request is still served, then the worker comes back", plus hung worker and crash loop). No real interactive session killed a worker.

**8. Outcome capture (PARTIAL).** `m4-acceptance.jsonl` (15 outcomes, 1 update): 13 of 15 outcomes join to a decision in the same log; a `reverted_edit` update (`inverse_edit`, offset 3 turns) joins to its decision; `test_failure_after_edit` (`node-test`, exit 1) recorded; corrections `en:thats_wrong` 1.0 (seq 2) and `en:undo` 0.8 (seq 3); one subagent-scope outcome joined to a subagent decision. Not fully shown:
- The two decision-less windows (seq 5, 6) are the injected messages (peer message, task notification) and were recorded **before** the injected-message fix; that they now keep the user's round open and are never scored is verified by `test/unit/outcome.test.ts` ("session 2 seq 5/6 replay …") and `d4699c7`, not by a re-run of a real session. The replay of the earlier sessions found 0 `harness_injected`.
- The `en:undo` correction (0.8) sits on seq 3 while the revert it asked for targeted seq 1: the correction is attached to the turn before the prompt that asked for the undo, by the current rule (a next prompt scores the previous turn). Whether that is "the appropriate round" is the open Phase 2 item "undo-family correction attribution when a revert has `offset_turns > 0`"; it is not fixed.

**9. Report.** `node bin/reflex.js report <file>` on each of `shadow-1`, `route-1`, `route-2`, `route-3`, `m4-acceptance`: exit 0, empty stderr, all ten sections, on 61, 71, 42, 18 and 70 decisions; all five together (deduplicated, 262 decisions, 9 sessions) also runs. Outcome rates are only present in `m4-acceptance` and every group there is below the 20-window minimum, so the report prints counts and the "insufficient data" line instead of rates. The shadow-1 latency section reproduces the figures in `docs/observations.md` (p50 823 ms, p95 1,136 ms, n = 12). There is no separate M5 "acceptance session": the latest recorded session is the M4 one.

**10. Privacy (MET, reworded).** Criterion as decided by the owner on 2026-09-19: no secrets, no home-directory paths, no user text beyond the redacted preview (at most 300 code points per decided prompt); project-relative paths are acceptable; `REFLEX_LOG_PROMPTS=1` adds the preview. *Revisited 2026-09-20: the preview default is now off (it was on through the archives cited below, recorded before this revisit).* Archive evidence (`check-archives.mjs` 10a–10d, all 278 archived records): no home-directory path, API key, token, JWT, PEM or Authorization value (10a); no free-text field other than `prompt_preview` and `forwarded.fallback_error` (the upstream's redacted error message), and the outcome, `outcome_update` and `harness_injected` records hold only hashes, counts and rule ids (10b); 47 previews, the longest exactly 300 code points (10c); 14 of the 47 contain a project-relative path such as `src/…`, which the criterion allows (10d). `worker.log` has none of these and no `apikey_` appears in any log. Tests: the TypeSafe key never reaches the upstream (`shadow.test.ts`, `route.test.ts`, `door-worker.test.ts`); Jev sees only the allow-listed state keys; `REFLEX_LOG_PROMPTS=0` omits the preview and a caller-set preview is never trusted (`decision-log.test.ts`).

**11. `npm test`.** Exit 0: 476 tests, 0 failed, 0 skipped, including typecheck and eslint. The preloaded guard (`test/support/no-network.ts`) throws on any non-loopback connection, so a green run is an offline run. The new tests use no network beyond loopback fakes.

To run: `TYPESAFE_API_KEY=apikey_… npm run test:live` (about 90 Jev calls). Until then `docs/observations.md` has no reasoning-vs-length result, and the README says so.
